# CargoCells — аудит ядра

**Дата:** 2026-08-07  
**Версия:** code audit v1  
**Scope:** APP -> Web/CoreAPI -> Warehouse -> Forwarder MVP -> report/reconcile -> outbound/print.

## 1. Методика и ограничения

Проверен текущий код `main` и существующая документация. Это **не полный production runtime audit**: без live DB здесь нельзя подтвердить фактические значения connector mappings, активные system tasks, состояние очередей, реальные индексы/объёмы таблиц и поведение внешнего ASER endpoint на текущий момент.

Приоритеты:

- **P0** — может прямо сейчас повреждать данные/останавливать основной pipeline;
- **P1** — высокий риск рассинхронизации или следующего серьёзного инцидента;
- **P2** — технический долг/масштабирование/безопасность;
- **P3** — cleanup/удобство.

# 2. Исправлено в ходе текущей диагностики

## AUD-001 — неверный порядок `confirmed_sync` и `to_send`

**Статус:** FIXED  
**Было:** `confirmed_sync=40`, `to_send=30`.  
**Проблема:** переход `confirmed_sync -> to_send` трактовался reconcile как downgrade.  
**Исправлено:** `confirmed_sync=25`, `to_send=30`.

Бизнес-смысл теперь соответствует pipeline:

```text
registration confirmed -> outbound ready -> sent
confirmed_sync          -> to_send        -> sended
```

**Следующее действие:** закрепить regression test; не считать numeric rank финальной архитектурой.

# 3. P1 — исправить до большого рефакторинга

## AUD-002 — state machine описана в нескольких местах и уже расходится

В `warehouse_sync_actions.php` runtime знает:

```text
for_sync, half_sync, error, confirmed_sync, to_send, sended, success
```

Но `warehouse_sync_process_definition_from_connector()` содержит старую схему:

```text
for_sync -> half_sync/confirmed_sync/error
half_sync -> confirmed_sync/error
confirmed_sync -> []
error -> for_sync
```

`to_send`, `sended`, `success` отсутствуют, а `confirmed_sync` ошибочно выглядит terminal.

**Риск:** UI/helper/будущая автоматизация начинает жить по другой state machine, чем реальный backend.

**Решение:** один `WarehouseOutStateMachine`/transition service + один contract, который используют runtime, helper UI и tests.

## AUD-003 — reconcile может голодать на старых неизменяемых строках

`warehouse_sync_reconcile_half_sync()` выбирает:

```sql
WHERE status IN ('for_sync','confirmed_sync','half_sync','error','success','to_send')
ORDER BY status_updated_at ASC, id ASC
LIMIT N
```

Если первые `N` записей не меняют status, их `status_updated_at` тоже не сдвигается. Следующий запуск снова получает те же самые старые строки.

**Риск:** при достаточном объёме новые записи могут долго или вообще не попадать в reconcile batch.

Особенно подозрительно включение уже продвинутых/terminal-like `success` и `to_send`.

**Решение:** отдельный `last_reconciled_at`/cursor, либо выбор только действительно ожидающих reconcile состояний + pagination/fair scheduling.

## AUD-004 — fast outbound path подтверждает локальное состояние раньше внешнего результата

В `warehouse_item_out_confirm_send` есть fast path:

1. использовать заранее подготовленный label payload;
2. напечатать label;
3. обновить локальный `warehouse_item_out` до `sended`;
4. запустить `run_add_package_to_container.php` background через shell `&`;
5. вернуть пользователю `ok` с сообщением, что синхронизация с форвардом идёт в фоне.

Если background add-to-container упал, локальная БД уже говорит `sended`.

**Риск:** склад считает посылку отправленной, внешняя система — нет.

**Решение:** outbox/job с подтверждаемым external state. Либо `send_pending_external -> sended`, либо отдельное `external_sync_status`.

## AUD-005 — `success` не имеет одного зафиксированного бизнес-смысла

`success` разрешён в mappings, rank и history, но в просмотренном outbound flow нет единственного формализованного события, которое обязано выставлять `success`.

Возможные трактовки конфликтуют:

- пакет добавлен в контейнер;
- контейнер закрыт;
- рейс закрыт;
- внешний report подтвердил финальный статус;
- workflow технически завершён.

**Решение:** определить один terminal criterion либо отказаться от `success` как warehouse state.

---

## AUD-006 — `error` ошибочно моделируется той же линейной шкалой rank

Сейчас:

```text
half_sync = 20
error = 20
confirmed_sync = 25
```

Из-за downgrade guard поздняя ошибка после `confirmed_sync`/`to_send` может быть проигнорирована как «откат».

Это может быть полезной защитой от устаревшего report, но сейчас это не explicit rule.

**Решение:** error/health вынести из progression rank или ввести явные transition rules по классу ошибки.

---

## AUD-007 — регистрация у forwarder реализована несколькими похожими pipeline

Как минимум:

- `commit_item_in_batch` в `warehouse_item_in_actions.php`;
- `warehouse_sync_item` в `warehouse_sync_actions.php`;
- manual stock registration helpers/actions.

Они частично повторяют:

- resolve connector;
- required fields;
- build payload;
- `run_add_package.php`;
- idempotent already-exists handling;
- audit/error processing.

**Риск:** исправление в одной ветке не попадает в остальные.

**Решение:** единый `ForwarderRegistrationService` с несколькими entrypoint'ами.

---

## AUD-008 — schema mutation выполняется из runtime request handlers

Код содержит многочисленные `CREATE TABLE IF NOT EXISTS` и `ALTER TABLE ... ADD COLUMN` внутри `ensure_*` функций, вызываемых обычными actions.

**Риск:**

- неожиданный DDL lock в production request;
- разный schema state между окружениями;
- невозможно точно сказать, какая версия DB соответствует какой версии кода;
- сложнее rollback.

**Решение:** versioned migrations. `ensure_*` временно оставить как compatibility guard, затем сделать read-only schema assertion.

---

## AUD-009 — APP имеет конфликтующий P1 handler

В `MainActivity.kt` flow/context code несколько раз назначает:

```text
MainActivity.onP1Single = dispatch...("p1_single")
```

но после большого блока setup присутствует безусловное:

```text
MainActivity.onP1Single = { openItemInOcrFromP1() }
```

**Риск:** server-driven mapping `p1_single` может быть перезаписан и работать не по `device-scan-config`.

**Решение:** один owner hardware-button routing; P1 OCR shortcut должен быть обычным configurable action, а не финальным override.

---

## AUD-010 — APP может полностью отключить TLS certificate/hostname verification

`allowInsecureSsl` используется для trust-all TLS и WebView `SslErrorHandler.proceed()`.

**Риск:** если флаг случайно включён в production, device login/session/API можно перехватить MITM.

**Решение:** insecure SSL разрешать только debug/dev build flavor; production binary должен игнорировать этот setting и требовать валидный TLS.

---

## AUD-011 — device unenroll в APP фактически stub

В UI есть TODO вместо реального `/api/device_unenroll`; локально выполняется delay и `onUnenroll()`.

**Риск:** пользователь думает, что устройство отвязано на сервере, хотя серверная запись/token могут остаться активными.

**Решение:** реальный revoke endpoint + server confirmation перед очисткой локального enrollment.

# 4. P2 — hardening и масштабирование

## AUD-012 — `MainActivity.kt` монолитный и содержит дублированные helpers

В файле есть одновременно локальные и top-level определения одинаковых helper concepts, например `fieldSelector`. Внизу присутствует исторический маркер:

```text
ВСТАВИТЬ В САМЫЙ КОНЕЦ MainActivity.kt
```

Это явный след накопительных patch-вставок.

**Решение:** разделить на `ScannerController`, `WebViewBridge`, `FlowEngine`, `HardwareKeyRouter`, `EnrollmentClient`, `OcrController`.

---

## AUD-013 — print infrastructure частично hard-coded в warehouse handler

В `warehouse_sync_actions.php` заданы compile-time/default constants для:

- CUPS host;
- queue;
- template paths;
- production print mode;
- debug layout flags.

Один PDF path содержит окружение `/home/makler/...`, тогда как рабочий проект может жить в другом deployment path.

**Решение:** printer profile/env/DB config, без environment-specific абсолютных путей в business handler.

---

## AUD-014 — report lookup имеет fallback через `LIKE` по JSON payload

Если нормальная tracking column недоступна, поиск может выполняться как substring match внутри `payload_json`.

**Риски:**

- full scan больших report tables;
- ложное совпадение tracking как substring;
- плохая масштабируемость.

**Решение:** нормализованная индексированная колонка tracking обязательна для production report table.

---

## AUD-015 — legacy Node/browser flow и PHP Forwarder flow живут параллельно

В `warehouse_sync_actions.php` всё ещё есть parser/runner для browser `steps` и Node script, одновременно operational registration использует PHP runners.

**Риск:** два способа выполнить одну business operation расходятся по поведению.

**Решение:** объявить canonical PHP path, пометить legacy browser path deprecated, удалить только после inventory реально используемых connector operations.

---

## AUD-016 — connector credentials хранятся непосредственно в таблице `connectors`

Schema содержит `auth_username/auth_password/auth_token/auth_cookies`.

**Решение hardening:** минимум — строгие DB/file permissions и masking; далее secrets store/env/vault. Operation JSON не должен содержать credentials.

---

## AUD-017 — declared-report helper зависит от reconcile для существующей outbound строки

`warehouse_forwarder_sync_declared_to_out()`:

- создаёт `to_send`, если outbound row отсутствует;
- если row уже есть с другим state, возвращает `skipped_existing_state`.

Это защищает от прямого перезаписывания state, но создаёт скрытый contract: **report import сам не продвинет существующий `confirmed_sync`; нужен reconcile**.

**Решение:** после появления transition service и import, и reconcile должны вызывать один transition resolver.

---

## AUD-018 — недостаточно автоматизированных regression tests для state transitions

Недавняя ошибка rank была бы поймана одним тестом:

```text
confirmed_sync + report Declared => to_send
```

**Решение:** state-machine unit tests + fixture-based connector report tests + API integration tests для outbound confirm.

# 5. Что в архитектуре уже сделано правильно

Не всё нужно переписывать. Полезные основы:

1. `core_api.php` имеет явный action routing вместо одного огромного switch-файла.
2. `device-scan-config` делает scanner flow server-driven и сохраняет Web-only fallback.
3. Connector report status mapping вынесен в DB config.
4. PHP Forwarder уже разделён на `Http/Services/DTO/Logging/...`.
5. Существует отдельный `forwarder_endpoints_contract.yaml`.
6. Background jobs вынесены в `system_tasks` + cron runner.
7. Есть `warehouse_sync_audit` и `warehouse_sync_trace`.
8. Forwarder report import умеет создавать stock-карточки и сохранять происхождение.
9. Flight/container sync имеет защиту от destructive deactivate при неожиданно пустом внешнем ответе.
10. Credentials в audit/result местами уже mask'ятся.

Главная задача — **не переписать систему, а свести эти хорошие куски к единому контракту**.

# 6. Runtime audit — следующий обязательный проход

Нужно снять с production только чтением:

### Connectors

- `connectors`: id/name/countries/is_active/base_url без секретов;
- `connectors_addons.status_targets_json`;
- `connectors_addons.report_out_statuses_json`;
- operation IDs/kinds без credentials.

### Warehouse state

Количество по каждому `warehouse_item_out.status`, возраст oldest/newest, дубли tracking/TUID, строки без stock item, строки без connector/country.

### Reconcile

- сколько строк попадает в первые 200;
- повторяются ли одни и те же ID;
- backlog по состояниям;
- фактические `status_downgrade_skipped`;
- время обработки.

### Background jobs

- active `system_tasks`;
- последний успешный/ошибочный run;
- batch backlog;
- cron frequency.

### Forwarder report

Для каждого активного connector/country:

- имя report table;
- наличие индексированной tracking column;
- список реальных external statuses за 30 дней;
- какие external statuses не покрыты mapping.

### Outbound

- `to_send` без label payload;
- `sended` без flight/container;
- `sended` с возможной external sync error;
- повторные outbound attempts по tracking.

Результат runtime-прохода нужно добавить в этот файл как Audit v2, не заменяя code findings.
